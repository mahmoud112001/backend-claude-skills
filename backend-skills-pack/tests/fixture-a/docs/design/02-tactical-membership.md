# 02 Tactical design: Membership

## Inputs
- docs/design/project-profile.md: modular monolith, one NestJS module per context; in-process domain events plus a transactional outbox per module; UUIDv7 ids generated by the application; RFC 9457 errors with a "code" member; no project rules file.
- docs/design/01-strategic.md: Membership row (owns REQ-28, REQ-29), context map rows Membership to Lending and Membership to Fines (integration event MemberRegistered), rows Catalog/Fines to Membership (separate ways), Published language of all four contexts, Ubiquitous language (Member, Card number, Signed-in member, Librarian), D1-7, Q-1, Q-9, Q-10.
- docs/design/00-project-brief.md: Actors (Visitor, Member, Librarian, System), REQ-28, REQ-29, Q-1, Q-9, Q-10, data row "Member: name, email, card number".
- Rulebook: .claude/skills/backend-design-team/references/default-rulebook.md (no project rules file).

## Decisions
- D2-1 One aggregate, Member, holding name, email and card number. Why: REQ-28 shows only these fields, and no rule ties two members together except card number uniqueness. Proposed.
- D2-2 Card number uniqueness (Q-10, proposed default "unique") is a set rule across Member instances. It is enforced at RegisterMember by a unique constraint in the membership store inside the same transaction that inserts the Member; no Member instance is changed by another. Why: only one aggregate is written, and the store rejects the duplicate atomically. Proposed.
- D2-3 Member id is a UUIDv7 generated by the application (profile id_convention). The card number is a separate value object and never the id (01 Ubiquitous language "Card number ... Not to be confused with Member id").
- D2-4 ResolveCurrentMember is a query, not a command: it maps the signed-in identity (supplied by the identity provider, Q-1) to a Member and a role and changes nothing (REQ-29, D1-7). A request with no identity, or one that maps to no Member and no Librarian role, is treated as a Visitor (REQ-29). Proposed.
- D2-5 The identity-to-member link is the verified email from the identity provider matched to Member.email (see OQ-M2), and the Librarian role is a claim of the identity provider, not a Membership record (see OQ-M3). Why: the brief shows no linking or staff screen (Q-1); this needs no new command or aggregate. Proposed.
- D2-6 MemberRegistered is the only integration event; its payload carries memberId, name, email and cardNumber so that both downstream contexts get what 01 says flows (Lending: id, name, email; Fines: id, card number). Source: 01 context map.
- D2-7 Edit and deactivate member are not designed (brief Q-9 default "out of scope"); no MemberChanged event exists, so downstream copies never change after registration. Source: brief Q-9.
- D2-8 Membership consumes no events and has no policies: 01 lists no context upstream of Membership. Source: 01 context map.
- Fixed F13: the 200-character name limit is no longer stated as fact in PersonName; it is open question RQ-5 with proposed default 200 characters.

## Open questions
| Id | Question | Why it matters | Proposed default |
|---|---|---|---|
| OQ-M1 | Is the card number unique (brief Q-10), and who issues it: typed by the librarian or generated? | Uniqueness constraint and the RegisterMember input (REQ-28, REQ-23). | Unique; typed by the librarian as shown on S5. |
| OQ-M2 | How is a signed-in identity linked to a Member (brief Q-1)? | ResolveCurrentMember (REQ-29) needs a stable key. | Match the identity provider's verified email to Member.email; email therefore unique across members. |
| OQ-M3 | Where does the Librarian role come from (brief Q-1, Actors)? | Who may call RegisterMember and every desk or admin operation. | A role claim from the identity provider; Membership only reads it. |
| OQ-M4 | What is the card number format (length, characters)? | Validation of RegisterMember; brief data row shows no format. | Non-empty, 1 to 32 letters or digits, stored trimmed and upper-case. |
| OQ-M5 | Is email required and must it be unique? | RegisterMember validation and OQ-M2; hold email (REQ-16) needs it. | Required, valid address syntax, unique case-insensitively. |
| OQ-M6 | Can members be edited or deactivated (brief Q-9)? | Without it, a wrong email or card number can never be fixed and downstream copies never change. | Out of scope now; a later MemberDetailsChanged integration event would be added. |
| RQ-5 | What is the maximum length of a member name? The brief shows no limit. | RegisterMember rejects longer names (invalid-name) and the store column size follows it (REQ-28). | 200 characters. |
