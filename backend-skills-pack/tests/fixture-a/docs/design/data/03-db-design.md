## Decisions
- D3-1 One PostgreSQL schema per context: `catalog`, `lending`, `fines`, `membership` (profile architecture_style). Only the owning NestJS module writes its schema. No project rule overrides this.
- D3-2 Ids are `uuid` columns filled by the application with UUIDv7 (profile id_convention). No database default generates ids.
- D3-3 Enumerated sets are `text` with a CHECK list, and their values are lowercase snake_case (*proposed*, DQ-5). Why: adding a value is a plain migration, unlike a PostgreSQL enum type.
- D3-4 Foreign keys exist only inside one schema. Cross-context ids are plain `uuid` columns listed as REF (DB-01). References between aggregates of the same module (for example loan to borrower) use FKs, because both sides are in one module and are never deleted.
- D3-5 Every FK is ON DELETE RESTRICT, except on the read model `catalog.book_availability` (CASCADE). Why: no aggregate is ever deleted (Catalog D2-9, Membership D2-7, Lending D2-9 keeps history), and RESTRICT stops a bug from silently erasing loans, holds, fines or payments.
- D3-6 No soft delete. History uses lifecycle states: `lending.book_copy.state = withdrawn`, `lending.loan.returned_at`, the closed values of `lending.hold.state`, and append-only `fines` ledger rows (Fines D2-2).
- D3-7 Money is `bigint` minor units (Fines D2-7). The currency is one `char(3)` column on `fines.account`, and fines and payments use the account currency, so currencies cannot be mixed (FQ-1, DQ-4).
- D3-8 Due dates are `date` (a calendar day in the library time zone). Instants are `timestamptz`, stored in UTC (*proposed*, DQ-1; Lending LQ-11, Fines FQ-3).
- D3-9 CQ-6 is resolved in the schema. The `version` of `lending.book_circulation` after the committing transaction is the `version` field of BookAvailabilityChanged, and it strictly increases per book. `catalog.book_availability.source_version` stores the last applied value, and the projection upserts only when the incoming version is higher. No extra Lending column is needed.
- D3-10 Each emitting module has an `outbox` table written in the same transaction as the state change (profile events_messaging, DB-05). The Lending outbox also carries the internal events that trigger policies across aggregates (LoanSlotReserved, LoanRefused, LoanEnded, CopyPlacedOnHoldShelf), so a crash between two transactions loses nothing (Lending D2-4).
- D3-11 `lending.outbox.deliver_not_before` implements the 3-day hold-shelf timer (Lending D2-8). The other modules have no delayed events, so their outboxes omit the column.
- D3-12 Each consuming module has an `inbox` keyed by (consumer, message_id), written in the handler's transaction. The worker redelivers an outbox row to all its handlers until every handler has succeeded, and a handler that already ran skips it via the inbox. A `lending.outbox` row with a non-null `target_consumer` goes to that one handler only (D3-L5). Membership consumes nothing, so it has no inbox (Membership D2-8).
- D3-13 The hold queue order comes from a per-book counter, `lending.book_circulation.next_hold_sequence`, which is unique together with `book_id` on `lending.hold` (REQ-7, Lending invariant g).
- D3-14 Catalog search uses the `pg_trgm` extension, with GIN indexes on `lower(title)` and `lower(author)` (CQ-3 proposed default, DQ-8).
- D3-15 Each constraint that rests on a proposed default from 02 names that default in Notes (CQ-1, CQ-2, CQ-8, LQ-6, LQ-9, FQ-2, OQ-M1, OQ-M4, OQ-M5). If an answer changes, only that constraint changes.
- D3-16 The design is split by module to stay under 300 lines (DOC-01). This file covers the shared decisions, Catalog and Membership; [03-db-design-lending.md](03-db-design-lending.md) and [03-db-design-fines.md](03-db-design-fines.md) hold the other two modules.
- D3-17 Each module that exposes an operation taking an `Idempotency-Key` (06 D6-8, D6-9) has an `idempotency_record` table in its own schema: `catalog` (addBook), `lending` (borrowBook, placeHold, addCopy, checkInCopy, and the optional key of renewLoan, cancelHold, withdrawCopy), `membership` (registerMember), `fines` (recordFinePayment). PK (caller, operation, key). Why one per module: only the owning module writes its schema (D3-1), and the record must commit with the command.
- D3-18 Idempotency protocol (*proposed*, technical). The handler takes `pg_try_advisory_xact_lock` on a hash of (caller, operation, key); if it is held, it answers `409 idempotency-key-in-use`. It then reads the record: same `request_hash` replays `status` and `body`, another hash answers `422 idempotency-key-reused`. Otherwise it runs the command and inserts the record **in the command's transaction**. A stored domain error (4xx other than 401, 429, `concurrency-conflict`) rolls the command back, so its record is inserted in a second short transaction under the same key; if that insert is lost, a retry re-runs a command that committed nothing, which is safe.
- D3-19 `request_hash` is the SHA-256 (32 bytes) of the canonical request (path parameters plus JSON body). `operation` holds the 06 operationId as spelled there (`addBook`), not snake_case, so the name is the same in every artifact (DOC-04); this is the one exception to D3-3.
- D3-20 Idempotency rows are hard deleted by a purge job once `created_at` is older than 24 hours (06 D6-8, AQ-2). They are technical records with no history value (DB-11).
- Fixed F2: `lending.outbox` gains nullable `target_consumer` (null = all handlers); the two CopyPlacedOnHoldShelf rows target NotifyHolderOnHoldShelf and ExpireHoldOnShelfDeadline (03-db-design-lending.md D3-L5).
- Fixed F3: added `catalog.idempotency_record`, `membership.idempotency_record` (here), `lending.idempotency_record` and `fines.idempotency_record` (module files); D3-17 to D3-20. Closes the storage half of 06 AQ-2; the 24-hour retention stays AQ-2.
- Fixed F5 (follow-on): DQ-3 is closed. accountVersion is the ordering key (02 Lending D2-11); `lending.borrower.fine_status_account_version` is compared and `fine_status_as_of` is display only.
- Fixed F6 (follow-on, 02 Lending D2-15): `lending.loan_slot` is no longer hard deleted on refusal; it gains `state` (reserved, refused), `refused_at` and `reason`, and refused slots are excluded from the 3-loan and one-per-book constraints (03-db-design-lending.md D3-L3).
- Fixed F8: the BookAvailability rebuild is the Lending maintenance job RepublishBookAvailability, which writes one BookAvailabilityChanged outbox row per `lending.book_circulation` row with its current version (03-db-design-lending.md D3-L6). DQ-2 now asks only about retention.

## Open questions
| Id | Question | Why it matters | Proposed default |
|---|---|---|---|
| DQ-1 | Which time zone is the library in, and is a loan due by the end of its due date? | `due_date date`, overdue list, days late (LQ-11, FQ-3). | One configured IANA zone; a loan is due by the end of `due_date` in that zone. |
| DQ-2 | How long are published outbox rows and inbox rows kept? BookAvailability no longer needs replay to be rebuilt (D3-L6). | Table growth; how long a failed delivery can be investigated. | Delete published outbox rows and inbox rows after 30 days. |
| DQ-4 | One currency for the library, or one per account? (FQ-1) | `fines.account.currency`. | One currency from configuration, copied onto each account when it opens. |
| DQ-5 | How are state values spelled in the store? | CHECK lists. | Lowercase snake_case (`on_hold_shelf`), mapped to the 02 names in code. |
| DQ-6 | What is the type of the librarian identity in `fines.payment.recorded_by`? (Q-1) | The identity provider is not chosen yet. | The provider's opaque subject, as text of 1 to 255 characters. |
| DQ-7 | What are the barcode format and length? 02 Lending says only non-empty. | CHECK on `lending.book_copy.barcode`. | Trimmed, 1 to 64 characters, unique as typed. |
| DQ-8 | Is accent-insensitive search needed, and may the `pg_trgm` extension be installed? | Search index (CQ-3). | Install `pg_trgm`; no accent folding. |

| Column | Type | Null | Default | Constraint | Notes (invariant / REQ) |
|---|---|---|---|---|---|
| book_id | uuid | no | none | PK | UUIDv7 |
| title | text | no | none | ck_book_title | BookTitle, trimmed, 1-500 chars (REQ-24, CQ-8) |
| author | text | no | none | ck_book_author | AuthorName, trimmed, 1-500 chars (REQ-24, CQ-8) |
| isbn | char(13) | no | none | uq_book_isbn, ck_book_isbn | ISBN-13 digits (CQ-1, CQ-2) |
| added_at | timestamptz | no | none | | |
| version | bigint | no | 1 | | optimistic concurrency |

## Enforced in code
| Invariant | Why not in the store | Where enforced |
|---|---|---|
| ISBN checksum (CQ-2) | Checksum arithmetic is domain logic; the store checks only the 13-digit form | Isbn value object, AddBook |
| BookAvailability ignores older events (CQ-6) | The condition depends on the stored row | Projection upsert `WHERE excluded.source_version > book_availability.source_version`, plus catalog.inbox |
| Full email syntax (OQ-M5) | The regex in the store is only a coarse guard | EmailAddress value object |
| Only a Librarian adds books or registers members (REQ-24, REQ-28) | Identity lives outside the store | API guard via ResolveCurrentMember |
| Member values never change after registration (OQ-M6) | Nothing is there to constrain because no update path exists | The Membership module exposes no update |
| One execution per idempotency key; `concurrency-conflict` and in-flight 409 are never stored (06 D6-8) | The key check spans the lock, the read and the command; the stored status cannot tell `concurrency-conflict` from other 409s | Idempotency interceptor of each module (D3-18); PK (caller, operation, key) is the last guard |
| Lending and Fines invariants | Listed with their tables | 03-db-design-lending.md, 03-db-design-fines.md |
