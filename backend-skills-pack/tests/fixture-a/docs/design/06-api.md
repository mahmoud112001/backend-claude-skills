## Decisions
- D6-1 The authoritative contract is the OpenAPI 3.1 file [06-api.openapi.yaml](06-api.openapi.yaml) (profile api_contract_file). It is split into module files to stay under 300 lines (DOC-01): [common](06-api.openapi-common.yaml), [catalog](06-api.openapi-catalog.yaml), [lending](06-api.openapi-lending.yaml), [membership](06-api.openapi-membership.yaml), [fines](06-api.openapi-fines.yaml). The root file is the entry point; this table and the contract must agree, and the contract wins on field shapes. The file is named `06-api.openapi.yaml`, not `openapi.yaml`, because this phase writes only `06-api*` files.
- D6-2 Only actor-triggered commands are exposed (10 command operations). The 10 policy-triggered commands, and the creation of BookCirculation, Borrower, HoldReadyNotification and Account (all `Created by` a policy), are never exposed (see Not exposed). Source: 02 Commands, Trigger column.
- D6-3 BorrowBook follows the Lending two-step borrow (Lending D2-4, LQ-1 proposed default). `POST /v1/loans` reserves a slot and returns `202 Accepted` with the generated `loanId` (D2-5) and `status: pending`. The handler waits up to 2 seconds (*proposed*) for the in-process outcome: LoanStarted gives `201` with `status: active`, the due date and the assigned copy `barcode`; LoanRefused gives `422 no-copy-available`. After a 202 (or a replayed 202, D3-L7) the client reads the outcome with getBorrowRequest (`GET /v1/loans/{loanId}`): `pending`, `active`, `ended` or `refused` with `refusalReason` (Lending D2-15).
- D6-4 Versioning is a path prefix `/v1` (*proposed*, the profile is silent, AQ-3). Within v1 only additive changes are allowed: new optional fields, new operations, new error codes. A breaking change gets `/v2` or a new operation; clients must ignore unknown fields and treat an unknown `code` by its HTTP status.
- D6-5 Errors are RFC 9457 `application/problem+json` with members `type`, `title`, `status`, `detail`, `instance` and the extension `code` (profile error_format). `type` is the relative URI `/problems/<code>` (*proposed*, AQ-4). `validation-failed` adds an `errors` array of `{pointer, code, detail}` (JSON Pointer to the field).
- D6-6 Error codes are kebab-case renderings of the 02 failure names (DuplicateIsbn becomes `duplicate-isbn`); Membership already uses kebab-case in 02 and is taken as is. The Errors table gives the 02 name for each code (DOC-04).
- D6-7 Status mapping (REST rules): malformed body or wrong types 400; no or bad token 401; role or ownership 403; unknown id 404; uniqueness, duplicate open item, version or in-flight key 409; a broken domain rule, including value-object rules from 02 Fails when (title-missing, invalid-isbn), 422; rate limit 429. 500 is only for server faults.
- D6-8 Idempotency. Creating commands (addBook, borrowBook, placeHold, addCopy, registerMember, recordFinePayment) and checkInCopy require an `Idempotency-Key` header (UUID, 1 per logical attempt). Keys are stored in each module's `idempotency_record` table, written in the command's transaction (03 D3-17), and kept 24 hours (*proposed*, purged per 03 D3-20), scoped to caller identity plus operation. A replay with the same body returns the first stored status and body with `Idempotent-Replayed: true`; the same key with another body gives `422 idempotency-key-reused`; a key still in flight gives `409 idempotency-key-in-use`. Responses 401, 429, 5xx and `concurrency-conflict` are not stored, so the same key can be retried. CheckInCopy needs a key because a late retry could end a newer loan of the same copy.
- D6-9 renewLoan, cancelHold and withdrawCopy accept an optional `Idempotency-Key` and are safe to retry without one, because each moves the item to a state that cannot be left (renewed, cancelled, withdrawn): a retry cannot apply twice and answers with the state error (loan-already-renewed, hold-not-open, copy-already-withdrawn).
- D6-10 Concurrency: no `ETag`/`If-Match` on v1 commands (*proposed*, AQ-10). Why: members never read the BookCirculation or Borrower version, and each command re-checks its invariants on the current state. The server retries an optimistic version conflict (DB-08 `version` columns) up to 3 times, then answers `409 concurrency-conflict` (retryable).
- D6-11 The signed-in member is the path alias `me` under `/v1/members` (one nesting level). The member id comes from ResolveCurrentMember at the API boundary (Lending D2-10, Fines D2-10, Membership D2-4); a client never passes another member's id. The path prefix does not imply ownership: `/v1/members/me/loans` is served by Lending, `/v1/members/me/fines` by Fines, each returning only its own module's model (API-07).
- D6-12 Copies are addressed by barcode in the path (`/v1/copies/{barcode}/check-in`), because the desk scans barcodes (REQ-20, REQ-26) and the barcode is unique (Lending D2-7, LQ-9). The path parameter is percent-encoded and must not contain `/` (AQ-9, DQ-7). FindCopyByBarcode stays an internal query of those handlers (02 Lending).
- D6-13 Lists use an opaque cursor (`cursor`, `limit` 1 to 100, default 20, *proposed*, AQ-6) and return `{items, nextCursor}`; `nextCursor` is null on the last page. Each list states a stable sort ending in its id.
- D6-14 Money in JSON is `{amountMinor: integer, currency: "ISO 4217"}` (Fines D2-7, D3-7). recordFinePayment takes `amountMinor` only (the account currency applies, D3-F3), so FQ-9 precision cannot be broken; zero or negative gives `invalid-payment-amount`.
- D6-15 Enumerated values in JSON are camelCase (`onHoldShelf`), mapped to the snake_case store values of D3-3 (DQ-5). Dates are ISO 8601 `date` (due dates, D3-8), instants are UTC `date-time`.
- D6-16 Authentication is a bearer token from the identity provider (Q-1 open, OQ-M3). SearchCatalog, GetBookDetails and ResolveCurrentMember accept anonymous calls (REQ-29, Catalog D2-8). A caller with a token but no Member record gets `403 not-member` on member operations; a member registered seconds ago whose MemberRegistered is not yet applied in Lending gets `409 borrower-unknown` (retryable).
- D6-17 201 responses carry `Location` only when a read operation for the created item exists (addBook to `/v1/books/{bookId}`). Other creations return the created item in the body and no `Location`, because 02 has no single-item query for them (AQ-8).
- D6-18 Every operation may answer `429 rate-limited` with `Retry-After` (security rules: rate limiting on all endpoints); limits are AQ-7.
- D6-19 A book added seconds ago may answer `404 book-not-found` on addCopy, placeHold and borrowBook until Lending applied BookAdded (outbox lag, Catalog D2-6); the error is marked retryable.
- D6-20 getBorrowRequest is `GET /v1/loans/{loanId}` (one nesting level, same resource as renewLoan), not `/v1/members/me/loans/{loanId}` as AQ-1 proposed. It reads only the signed-in member's loans and slots (02 GetBorrowRequest), so another member's loanId answers `404 loan-not-found`, not 403: the query is scoped to the caller, and nothing is acted on (AQ-5 covers commands only).
- Fixed F4: placeHold lists `borrower-unknown` (409, retryable), following 02 Lending PlaceHold `Fails when` BorrowerUnknown; the lending contract `x-error-codes` and the Errors table agree.
- Fixed F6: added query operation getBorrowRequest (`GET /v1/loans/{loanId}`, Lending GetBorrowRequest, D2-15) returning the Loan with status `pending`, `active`, `ended` or `refused`; `Loan` gains `returnedAt`, `refusedAt`, `refusalReason`. Closed AQ-1.
- Fixed F7: `Loan` has `barcode` (the copy LendCopy assigned, from Loan.copyId), null while pending or refused. The matching rule at the shelf stays RQ-2.
- Fixed F10: registerMember `email` has `maxLength: 254` in the membership contract, matching 03 `ck_member_email`.
- Fixed REV-03: REQ-30 (pick up a shelved hold copy) maps to borrowBook, following the proposed default of brief RQ-1: the holder uses Borrow and the shelf copy is lent to them. No new operation; RQ-1 stays open (see Open questions). If RQ-1 chooses a desk action, a new Librarian command operation is added in v1 (additive, D6-4) once 02 defines the command.
- Fixed F3 (follow-on): closed AQ-2; idempotency storage is the per-module `idempotency_record` table (03 D3-17 to D3-20), D6-8 cites it.

## Conventions
| Topic | Rule | Source |
|---|---|---|
| Style | REST over HTTPS, JSON bodies | profile api_style |
| Contract | OpenAPI 3.1, root [06-api.openapi.yaml](06-api.openapi.yaml) | profile api_contract_file, D6-1 |
| Paths | kebab-case plural nouns, `/v1` prefix, one nesting level, non-CRUD actions as `POST /<things>/{id}/<verb>` named after the 02 command | profile naming_convention, D6-4 |
| JSON fields | camelCase; enum values camelCase | profile naming_convention, D6-15 |
| Operation ids | camelCase of the 02 command or query name | DOC-04 |
| Ids | UUIDv7 strings generated by the server; never client-chosen | profile id_convention |
| Pagination | opaque cursor, `limit` 1 to 100, stable sort stated per list | D6-13 |
| Versioning | `/v1`, additive only within a version | D6-4 |
| Errors | RFC 9457 problem+json with `code` | profile error_format, D6-5 |
| Idempotency | `Idempotency-Key` header, 24 hours, replay returns first response | D6-8, D6-9 |
| Auth | bearer token; role and member resolved by ResolveCurrentMember | D6-16 |
